CHAPTER 00

这份文档怎么用

很多人学 JVM 的方式是背名词：堆分新生代老年代、Metaspace 替代永久代、-Xmx 设最大堆。说的时候都对，但一旦线上告警「容器被 OOMKilled」，就完全不知道从哪下手。这份文档的目标是给你一条完整的因果链。

先建立三个认知层次

层次一 · 结构
内存被分成哪几块
每块的归属（线程私有 / 共享）、存什么、谁来回收、满了报什么错。这一层是骨架。
层次二 · 参数
每个参数控制哪一块
-Xmx 只管堆、-Xss 只管线程栈、堆外参数在别处。参数记错，等于调了个寂寞。
层次三 · 机制
出问题时谁先死
堆涨满是 Java OOM，容器涨满是 OOMKilled；两者根因不同、证据不同、处置不同。

CHAPTER 01

JVM 是什么：结构与运行链路

先纠正一个常见误解：JVM 不只是「一个 Java 虚拟机」，它是一套规范加上至少一个实现。面试时如果说「JVM 就是 HotSpot」，会被认为概念混淆。

JVM 是规范，HotSpot 是实现

  • JVM 规范（JVM Specification）Oracle 定义的语言无关虚拟机行为标准：.class 文件格式、字节码指令集、运行时数据区布局、类加载与链接规则、线程模型。HotSpot、OpenJ9、GraalVM、Azul Zing 都实现了这份规范。
  • HotSpot（OpenJDK 默认实现）目前的事实标准。面试默认讨论的就是它。
  • GraalVM含 Graal 编译器（更快启动、更好的峰值性能）与 LLVM 语言的提前编译能力。
  • OpenJ9 / Zing低内存占用场景常见，容器冷启动比 HotSpot 更快。

四大子系统

子系统职责出问题时
类加载子系统 读取 .class → 校验 → 解析 → 初始化；双亲委派模型决定类从哪个 ClassLoader 加载 ClassNotFoundException、NoClassDefFoundError、Metaspace 泄漏
运行时数据区 内存分区：堆、方法区、虚拟机栈、本地方法栈、程序计数器 OutOfMemoryError、StackOverflowError
执行引擎 解释器 + JIT 编译器（C1/C2）+ 垃圾回收器 GC 频繁、长尾毛刺、CPU 飙高
本地接口（JNI） 加载本地动态库，System.loadLibrary 走这里 native 方法段错误、unable to create native thread

从 main 方法到字节码执行

  1. STEP 1 启动与初始化 JVM 进程启动，读取 JAVA_HOME、解析命令行参数、创建类加载器。此时 JVM 还没有加载任何业务类。
  2. STEP 2 内存区域就位 按 -Xms 预分配堆、创建 Metaspace、CodeCache、线程栈等结构。这一步决定了后续的内存上限。
  3. STEP 3 加载 main 类 AppClassLoader 按双亲委派加载 com.example.Main，链接（验证→准备→解析）后初始化静态字段与静态代码块。
  4. STEP 4 创建主线程 为 main 线程分配 Thread 对象、虚拟机栈、程序计数器，栈上压入 main() 的栈帧。
  5. STEP 5 解释执行 + JIT 编译 字节码先由解释器执行，热点方法（默认调用 2000 次或循环回边 15000 次）被 C1/C2 编译成本地代码，后续直接执行本地代码。
  6. STEP 6 GC 介入 分配速率超过回收能力时触发 GC。G1 优先在新生代回收，必要时才做 Mixed GC 回收老年代。

常见误区

「Java 是解释执行所以慢」——只对了一半。现代 JVM 默认开启分层编译（Tiered Compilation），启动阶段用解释器 + C1 快速编译保证启动速度，热点方法交给 C2 做激进优化。真正纯解释执行只在 -Xint 或早期版本出现。

「只有堆和 Metaspace 有 GC」这句话的准确含义

这句话是对面试标准答案的精炼，但表述有点粗糙。严谨的说法是：

  • GC 只管理堆里的对象。JVM 的垃圾收集器（Serial / Parallel / G1 / ZGC）只扫描堆，判断哪些对象不可达并回收。
  • Metaspace 没有专门的 GC，但它的回收由「类加载器卸载」触发。当一个 ClassLoader 加载的所有类都不再被引用、且该 ClassLoader 本身也不可达时，它对应的 Metaspace 内存被释放。这个过程由 JVM 在特定时机（如 Full GC、类卸载检查）执行。
  • 栈不需要 GC，因为栈帧的生命周期是确定的：方法进入时压栈，方法返回时出栈。栈上的局部变量表指向堆对象的引用，堆对象被回收后，这些引用自然变成 null，栈帧本身也随之销毁。这是「确定性的生命周期」，不需要也不能用 tracing GC 管理。

为什么栈不能用 GC？

GC 的前提是「无法静态判断一个对象是否还活着」，需要从 GC Roots 做可达性分析。栈上的对象是确定性的——方法返回必然销毁。用 GC 扫栈既没意义也会带来巨大开销。JVM 的取舍是：栈上只放引用和基本类型（原始类型直接存值，不指向堆），栈帧结构由编译器静态确定，可以像函数调用一样精确管理。

CHAPTER 03

内存比例：到底该怎么分

「每个分布都是什么比例」这个问题，没有标准答案——因为它取决于容器 limit、业务类型和 GC 选型。但有可用的经验基线和计算方法，这比背一个固定百分比有用得多。

先看默认值：JVM 自己会怎么猜

区域未显式配置时的默认行为版本差异 / 坑
堆最大容量 -Xmx 默认 = 物理内存的 1/4 JDK 8u191+ 与 JDK 10+ 引入了容器感知（UseContainerSupport），会读 cgroup limit 重新计算；但 cgroup v2 的嵌套层级需取所有父级 limit 的最小值，多层限制环境仍可能算错
堆初始容量 -Xms 默认约物理内存的 1/64 与最大堆差距过大时，堆会反复扩缩容，影响延迟稳定性
Metaspace 无上限（受物理内存限制），初始高水位约 21MB 这是最危险的默认值。泄漏时不会自己停，会一路吃到把容器撑爆，最后表现为 OOMKilled 而不是 OutOfMemoryError，丢失排查线索
直接内存 JDK 8u 默认 = -Xmx；JDK 9+ 默认 = -Xmx + 堆外余量 等于把堆外的安全边际也吃掉了，容易在容器里直接超限
线程栈 -Xss 默认 1MB（64 位平台） 默认线程数上限约 300~500 就能吃掉 300~500MB，与 -Xmx 完全独立
Code Cache 默认 240MB（分层编译） 大量动态代理 / Lambda 会撑大 CodeCache

重点提醒

Metaspace 默认为无上限是容器时代最常见的坑之一。很多团队的 OOMKilled 事故，根因是 Metaspace 泄漏而非堆溢出——因为 JVM 从不主动说「我 Metaspace 满了」，它只会一直要内存，最后被内核杀掉，日志里什么异常栈都没有。

区域推荐比例16GB 容器建议值依据

堆内比例：新生代 vs 老年代

堆内部的比例由两个参数控制：-XX:NewRatio（新生代 : 老年代）和 -XX:SurvivorRatio（Eden : S0 : S1）。

  • -XX:NewRatio=2（默认）→ 新生代 : 老年代 = 1 : 2，即新生代占堆的 1/3，老年代 2/3。
  • 短生命周期对象为主的服务（Web、RPC、网关）：-XX:NewRatio=1（各半）能显著降低老年代压力。
  • 长生命周期对象为主（缓存、大对象）：保持默认或调大老年代比例。
  • 现代 G1 / ZGC 下，NewRatio 的影响被削弱——G1 会自适应调整，ZGC 基本不需要分代参数。

别踩这个坑

很多团队为了「让老年代大一点」设 -Xmn。但 G1 下 -Xmn 会禁用新生代自适应，G1 无法再根据回收压力调整新生代大小，反而常常导致更频繁的 Full GC。G1 下建议用 -XX:NewRatio 而非 -Xmn，或者干脆交给默认值。

CHAPTER 04

Metaspace 到底是什么

Metaspace 这个名字容易误导人——它不是「元数据空间」的堆外版本，它仍然在堆外，但由 JVM 自己管理。理解这一点，后面的排查逻辑就顺了。

从永久代到 Metaspace

维度永久代（PermGen，JDK 7 及以前）Metaspace（JDK 8 起）
位置堆的一部分本地内存（堆外）
大小控制-XX:PermSize / -XX:MaxPermSize-XX:MetaspaceSize（初始高水位）/ -XX:MaxMetaspaceSize（上限，默认无限制）
字符串常量池在永久代在堆中（-XX:+StringTable 相关）
典型异常PermGen space OOMMetaspace OOM
OOM 时的现象堆和永久代互相挤占，容易误判堆正常，Metaspace 单独爆掉，定位清晰

Metaspace 里到底装了什么

  • 类的元数据（Class Metadata）类的结构信息：字段表、方法表、方法字节码、注解、常量池引用、继承关系、接口列表。这是主体。
  • 运行时常量池（Runtime Constant Pool）类的编译期常量池在运行时的表示，包含字面量与符号引用。
  • 方法字节码与 JIT 相关元数据方法的 Code 属性、异常表、局部变量表（LocalVariableTable）——后者是调试信息，很占空间。
  • MethodHandle / Lambda 相关每个 lambda 表达式首次执行时会生成一个隐藏类（hidden class），其元数据进入 Metaspace。
  • 压缩类空间（Compressed Class Space）存放类对象（java.lang.Class 实例）的元数据部分，与普通 Metaspace 分开管理，默认上限 1GB。

为什么 Metaspace 不做常规 GC

因为类加载和卸载的频率极低（通常只有几百上千个类），而 tracing GC 的成本与之不成比例。Metaspace 采用的是「按 Chunk 分配、类加载器卸载时整块释放」的策略：

  1. 类加载时从 Metaspace 分配一个 Chunk（默认 21MB 的 metaspace chunk，或按需扩展）。
  2. ClassLoader 加载的所有类都不再可达、且 ClassLoader 本身也不可达时，该 ClassLoader 的所有 Metaspace 内存被释放。
  3. 释放的触发时机是 Full GC 或 Metaspace 压力触发的检查。

这就是「类加载器泄漏」在容器里最致命的原因

如果 ClassLoader 一直被某个静态引用链吊住（比如动态代理持有、ThreadLocal 持有、JDBC 驱动注册表持有），它加载的所有类的元数据就永远无法释放。表现出来是：堆看起来正常（只涨了 5%），但 Metaspace 一路涨到容器上限，进程被 OOMKilled。这类问题不设 -XX:MaxMetaspaceSize 就完全无法察觉。

Metaspace 泄漏的四个常见来源

来源机制识别特征
动态代理 / CGLIB 每次 new Proxy() 都生成一个新的 Class + 一个新的 ClassLoader LoadedClassCount 单调递增；jcmd GC.class_histogram 里代理类数量暴涨
频繁热部署 / DevTools 重启 每次重启新建 WebAppClassLoader，旧的不卸载 类数量阶梯式增长，伴随 Metaspace 阶梯式上涨
Lambda 表达式过多 每个 lambda 首次执行生成隐藏类 类名形如 Foo$$Lambda$123/0x0000... 数量大
JDBC 驱动 / 插件动态注册 驱动被注册进全局 DriverManager，持有定义它的 ClassLoader jcmd VM.classloaders 看到大量 ClassLoader 且无对应 class

Metaspace 排查命令

排查步骤

1）看趋势　jcmd <pid> GC.heap_info 里的 Metaspace used，或监控 jvm_memory_bytes_used{area="nonheap"}。

2）看类数量（最灵敏的指标）

jcmd <pid> VM.classloader_stats        # 各 ClassLoader 加载的类数量
jcmd <pid> VM.classloaders             # ClassLoader 实例列表 + 是否存活
jcmd <pid> GC.class_histogram | head -30

3）看谁在加载　jcmd <pid> VM.class_hierarchy <classname> 可以追溯类的加载链。

4）算「应该释放但没释放」的量　对比 GC.class_histogram 里的类总数与 LoadedClassCount，或用 jcmd <pid> VM.native_memory summary（NMT，见第 15 章）看 Class 段占用。

经验值

普通 Spring Boot 应用稳定态 Metaspace 约 100~250MB。如果 1 小时内从 200MB 涨到 800MB，一定有泄漏。给 -XX:MaxMetaspaceSize=256m 后，泄漏会在几分钟内以 OutOfMemoryError: Metaspace 的形式暴露——这比被 OOMKill 好得多，因为有堆栈、有 dump。

TLAB：为什么需要它

多线程并发分配对象时，如果直接操作 Eden 的指针会产生 CAS 竞争，吞吐急剧下降。JVM 的解法是：每个线程预先从 Eden 划走一块私有区域（TLAB），分配时只需移动线程私有指针，完全无锁。TLAB 用满了再申请新的一块。TLAB 剩余空间不足分配的对象，会被分配在堆外（Eden 之外），这是「明明堆还有空间却 OOM」的少见原因之一。

晋升老年代的四条路径

  1. 年龄达标：对象在 Survivor 区每熬过一次 Minor GC 年龄 +1，达到 -XX:MaxTenuringThreshold（默认 15，G1 下默认 15）后晋升。
  2. Survivor 放不下：大对象或同年龄对象过多时，直接进老年代。
  3. 大对象：超过 -XX:PretenureSizeThreshold（Serial/Parnew 有效，G1 下不适用）直接进老年代。
  4. 动态年龄判定：Survivor 中同龄对象总和超过一半空间时，该年龄及以上的对象全部晋升（防止 Survivor 被撑爆）。

晋升失败的真正含义

晋升失败（Promotion Failure）不是「对象太大」，而是：Minor GC 结束时，Survivor 区放不下需要晋升的对象，或并发标记阶段结束后老年代没有足够空间容纳存活对象。这会触发 Full GC。
后果链条是：晋升失败 → Full GC → 回收后仍放不下 → 堆重构（Heap Retrashing）→ CPU 飙升 + 停顿数秒 → 请求堆积 → 雪崩。这是「明明堆内存够却频繁 Full GC」的典型解释。

CHAPTER 06

参数体系：-Xmx / -Xms / -Xss 全解

JVM 参数有几百个，但真正需要你在生产环境亲手调过的不超过二十个。这章把它们按「控制哪个区域」归类，面试和实战都用得上。

堆相关

参数含义默认值怎么用
-Xms 初始堆大小（committed） 约物理内存 1/64 与 -Xmx 设成一样，避免运行期反复扩缩容
-Xmx 最大堆大小（上限） 物理内存 1/4（容器感知后会重算） 必须显式设置。容器里这是最重要的一个参数
-Xmn 新生代大小 随 NewRatio 推导 G1 下慎用，会禁用新生代自适应
-XX:NewRatio 新生代 : 老年代 2（新生代占 1/3） 短生命周期对象为主时设 1
-XX:SurvivorRatio Eden : S0 : S1 8（8:1:1） 晋升过快时调大 Survivor（如 10）
-XX:MaxTenuringThreshold 对象最大晋升年龄 15 大对象多时可调到 6~8，配合 Survivor 调大

为什么建议 -Xms = -Xmx

因为 -Xms 是「操作系统已经为进程预留并映射的物理页」，-Xmx 只是「JVM 允许增长的上限」。如果 -Xms 小于 -Xmx：

  • 堆需要扩容时，JVM 必须向操作系统申请新内存并逐页 touch，这个过程是 STW 的，会造成延迟毛刺；
  • 堆缩容时，JVM 归还内存给操作系统，导致 RSS 下降，下一次扩容又要重新申请，RSS 曲线会出现锯齿；
  • 在容器里，频繁申请/释放会让 oom_score 变化，可能导致还没到 limit 就被提前 OOMKill。

所以生产环境一律 -Xms = -Xmx。唯一例外是某些需要「快速失败」的场景——设置很小的 -Xmx 让 OOM 尽早暴露，属于特殊用途。

Metaspace 相关

参数含义默认值
-XX:MetaspaceSizeMetaspace 首次触发 Full GC 的高水位（不是初始大小）约 21MB
-XX:MaxMetaspaceSizeMetaspace 上限无限制（危险）
-XX:CompressedClassSpaceSize压缩类空间上限1GB
-XX:MinMetaspaceFreeRatio / MaxMetaspaceFreeRatioGC 后 Metaspace 空闲比的高/低水位，决定是否触发类卸载40 / 70

线程栈相关

参数含义默认值怎么用
-Xss / -XX:ThreadStackSize单线程栈大小1MB（64 位）Netty / 高并发 IO 线程用 512k；需要深递归的业务用 1m~2m
-XX:MaxDirectMemorySize直接内存上限≈ -Xmx（JDK 9+ 略有不同）容器里必须显式设，否则堆涨满时直接内存还有一倍空间
-XX:ReservedCodeCacheSizeCode Cache 大小240MB一般不用改

GC 相关（按收集器）

收集器启用参数适用场景关键调优参数
G1 -XX:+UseG1GC（JDK 9+ 默认） 通用默认选择。堆 4GB ~ 64GB，延迟要求中等，业务延迟敏感 -XX:MaxGCPauseMillis（默认 200ms）、-XX:G1HeapRegionSize、-XX:InitiatingHeapOccupancyPercent
ZGC -XX:+UseZGC（JDK 17 生产可用，21+ 为主推） 大堆（> 100GB）、超低延迟要求（亚毫秒级停顿）、内存占用高的容器 -XX:MaxGCPauseMillis（默认 10ms）、-XX:SoftMaxHeapSize
Parallel GC -XX:+UseParallelGC 批处理、离线任务、吞吐优先、延迟不敏感 -XX:ParallelGCThreads、-XX:MaxGCPauseMillis
Shenandoah -XX:+UseShenandoahGC 超低延迟，停顿时长与堆大小无关 较少调
CMS -XX:+UseConcMarkSweepGC 已废弃 JDK 14 弃用，JDK 17 已移除，无法启用

CMS 为什么被移除

三个原因叠加：

  1. 碎片化：CMS 是标记-清除算法，不整理内存。并发标记期间新对象不断分配，可能触发「promotion failed」，被迫做 Full GC（而且是单线程压缩式 Full GC，停顿极长）。
  2. 浮动垃圾：CMS 只能清除「已标记」的对象，标记阶段刚结束进入并发清扫的对象会一直堆积到下次 GC，内存占用会先涨后降。
  3. 维护成本高：CMS 有大量调优参数（CMSInitiatingOccupancyFraction、CMSFullGCsBeforeCompaction…），且与 G1/ZGC 的实现差异大，代码里散落的 CMS 参数无法平滑迁移到新收集器。

OpenJDK 团队在 JDK 8 时代就开始用「CMS + Parallel Old 的组合作为 G1 的对照基准」，G1 的目标就是全面取代它。JDK 9 弃用、JDK 14 正式弃用、JDK 17 移除，是这条路径的终点。

启动参数怎么设：三种环境

「参数设在哪里」比「参数设什么」更容易出错。Spring Boot 尤其坑：-jar 后面的参数不是 JVM 参数，而是传给 main 的应用参数。

三种环境的设置方式

环境写法说明
直接运行 java -Xmx2g -Xms2g -jar app.jar JVM 参数必须在 -jar 之前

最经典的两个坑

坑 1：-jar 位置错误
java -jar app.jar -Xmx2g → -Xmx2g 成了 main(String[] args) 的第一个参数，JVM 完全没收到堆参数。Spring Boot 会把它当作配置项忽略掉，一切「看起来正常」，但堆用的是默认值。

坑 2：exec 形式无法展开变量
ENTRYPOINT ["java", "-jar", "app.jar"] + ENV JAVA_OPTS=... → 环境变量根本没用上。必须改成 ["sh","-c","java $JAVA_OPTS -jar app.jar"]。

Deployment 片段

  - name: JAVA_TOOL_OPTIONS
    value: >-
      -Xms2g -Xmx2g

为什么不推荐 JVM 参数写在 application.yml

Spring Boot 的 spring.aot.*、Actuator、某些 APM agent 都可能需要 JVM 层面的协作；而更关键的是，JVM 参数必须在 JVM 启动时生效，Spring Boot 的配置在 JVM 启动之后才加载。把 -Xmx 放进 yml 是无效的——这是很多人「配了但不生效」的原因。

「能不能直接用默认值」

生产环境能不能不设这些参数，全用默认值？

不能，而且是很危险的做法。理由有四：

  1. 默认值是按「物理机」设计的，不是按「容器」设计的。JDK 8 时代 JVM 看到的是宿主机内存（可能 64GB），算出的堆上限远超容器 limit——这是 OOMKilled 的头号来源。虽然 JDK 10+ 有容器感知，但 cgroup v2 嵌套场景仍会算错。
  2. Metaspace 默认无上限。泄漏时不会自己报错，一路吃到容器上限被 OOMKill，连异常栈都没有。
  3. 直接内存默认 ≈ -Xmx。等于把堆外安全边际完全放弃，堆涨满时直接内存还有同等空间。
  4. 默认的 -Xms 远小于 -Xmx。堆反复扩缩容带来延迟毛刺和 RSS 锯齿。

结论：至少必须显式设置 -Xmx、-Xms、-XX:MaxMetaspaceSize、-XX:MaxDirectMemorySize 这四项，其余按业务调。

ThreadStorm.java · 核心片段

/** 每个线程持有的业务对象，用来消耗堆内存。 */
static final class Payload {
    final byte[] buffer = new byte[64 * 1024];  // 64 KB
    final String name;
    Payload(String name) { this.name = name; }
}

public static void main(String[] args) throws Exception {
    int maxThreads = args.length > 0 ? Integer.parseInt(args[0]) : 5000;

    for (int i = 0; i < maxThreads; i++) {
        Thread t = new Thread(() -> {
            for (int k = 0; k < 10; k++) {
                new Payload("p-" + i);   // 持续消耗堆
            }
            while (true) {                // 保持存活，栈空间才真正占用
                Thread.sleep(60_000);
            }
        }, "worker-" + i);
        t.setDaemon(true);
        t.start();
    }
}

实验要验证的四个认知

  1. 线程栈不受 -Xmx 约束。把 -Xmx 从 64m 调到 2g，堆的 OOM 消失了，但 RSS 依然暴涨——因为栈在堆外。
  2. 堆和 Metaspace 是两条独立的边界。把 MaxMetaspaceSize 调小，会先得到 OutOfMemoryError: Metaspace，此时堆可能还剩 80%。
  3. 「-Xmx 设大点没事」是错的。容器里 -Xmx > limit 会导致进程还没来得及 GC 就被内核杀掉，连 dump 都拿不到。
  4. 线程数是内存的主要放大器。默认 -Xss1m 时，1000 个线程就是 1GB 堆外内存。线程池化不只是性能优化，更是内存管控手段。
CHAPTER 09

外部 OOM vs 内部 OOM

「内」「外」指的是相对于 JVM 的内存管理器而言：内部是 JVM 管的区域自己满了；外部是 JVM 管不到（或没管）的区域把整个进程撑爆了。

一句话区分

内部 OOM
OutOfMemoryError
JVM 自己发现某个受管区域（堆 / Metaspace / 直接内存）分配失败，抛 Java 异常，有完整堆栈，进程还活着。
外部 OOM
OOMKilled
操作系统内核发现进程 RSS 超过 cgroup limit（或宿主机 OOM Killer 介入），直接 SIGKILL，没有异常栈、没有 dump，进程瞬间消失。

RSS
（Resident Set Size）		 进程当前实际驻留在物理内存中的页数总和（含共享库分摊） top 的 RES 列、/proc/<pid>/status 的 VmRSS、cAdvisor

VSZ 为什么经常是个天文数字

64 位 JVM 会为每个线程预留 1MB 栈地址空间，为堆预留大块连续地址，为 metaspace 预留 1TB 虚拟空间。这些大多没有实际占用物理页。所以 top 里看到 VSZ 20GB 而 RSS 只有 800MB 是完全正常的。判断内存用超了，要看 RSS，不要看 VSZ。

RSS 和 -Xmx 为什么不相等

RSS > -Xmx 的六个原因：

  1. 堆外内存：线程栈（线程数 × -Xss）、Metaspace、CodeCache、直接内存、GC 自身的 Remembered Set 等，全都不计入 -Xmx。
  2. 堆的 committed 可能大于 used：JVM 已申请但当前没有对象占用的页，仍算在 RSS 里（除非被 unmap）。
  3. live set 小于 used：堆里 30%~70% 往往是垃圾，RSS 统计的是「已占用的页」，不区分里面有没有活对象。
  4. GC 不会立刻归还内存：Full GC 后 JVM 也不一定 shrink 堆；G1 的 Humongous Region 释放后可能保留为待复用状态。
  5. glibc malloc arena：多线程程序会创建多个 arena（默认最多 8 × CPU 核数），每个 arena 有自己的空闲链表，会造成显著的内存碎片浪费。这个在容器里尤其明显。
  6. JNI / native 库：Netty 的 epoll、压缩库、数据库驱动的 native 内存。

推论：容器 limit 绝不能等于 -Xmx

如果 limit == -Xmx，那么堆还没满，进程就已经被内核杀了——因为堆外的部分还没算进去。常见的安全比例是 -Xmx ≤ limit 的 50%~60%。这就是第 14 章要展开的核心问题。

CHAPTER 11

线程数与内存的关系

线程是 Java 内存占用的「放大器」。理解每个线程的真实成本，才能在容量规划时做出正确决策。

一个线程的真实成本

组成在哪里大小说明
线程栈 堆外 -Xss，默认 1MB 实际占用按需增长，但虚拟空间是全量预留
Thread 对象 堆内 约 400~500 字节 含 name、priority、group、target、栈指针等字段
TLAB 堆内（Eden） 默认几十 KB ~ 几百 KB 每线程一块，大对象多时可调 -XX:-UseTLAB 关闭
ThreadLocal 及其 Entry 堆内 不定 每个线程一份，未 remove 会成为泄漏源
native 线程结构 内核 约 8~16KB（pthread + TLS） 受 pids.max / threads-max 限制

估算公式

堆外内存估算

堆外内存 ≈ 线程数 × (-Xss + TLAB + Thread 对象 + native 结构)
         ≈ 线程数 × (-Xss + 0.5MB)      # 粗略估算

举例：2000 线程，-Xss1m
  线程栈   = 2000 × 1MB   = 2000 MB
  TLAB     = 2000 × 0.1MB =  200 MB
  Thread   = 2000 × 0.5KB =    1 MB
  合计                        ≈ 2.2 GB  ← 全部在堆外！

线程数失控的典型症状

java.lang.OutOfMemoryError: unable to create new native thread —— 这个异常不是堆不够，而是操作系统拒绝创建新线程。常见原因：

  • 线程数超过 pids.max（K8s 默认 limit 无限制，但 --pids-limit 会限制）
  • 超过 vm.max_map_count 或虚拟内存限制
  • 宿主机 threads-max 或 ulimit -u 达到上限
  • 内存已经紧张，内核无法为新线程分配栈页

注意：这个异常常被误判为「内存不足」，实际根因往往是内存不足导致的线程创建失败——修内存比改线程池更有效。

线程池怎么定大小

任务类型核心线程数依据
CPU 密集型（计算、加密、序列化）N + 1N = CPU 核数；上下文切换成本高，不宜过多
IO 密集型（数据库、RPC、文件）N × (1 + W/C)W=等待时间，C=计算时间；实践中常简化为 2N ~ 4N
Netty EventLoop2 × N一个 Boss + 一个 Worker；绝不能改成阻塞池
Dubbo / gRPC 线程池按 CPU × 2~4底层有 Netty 支撑，注意两池叠加的总线程数

别忘了 Tomcat / Tomcat 之外的框架线程

一个 Spring Boot 应用的实际线程数 = Tomcat 工作线程（默认 200）+ Tomcat acceptor（默认 10）+ JVM 后台线程（GC ~ 10 + JIT ~ 10）+ 业务线程池 + 各种中间件客户端线程 + APM 探针线程。真实场景里 500~800 线程很常见。

压测时必须打开线程快照确认：jcmd <pid> Thread.print | grep -c '"'，或者用 Arthas 的 thread -n 3 看最耗时的线程。

先说 PID

PID 是什么

PID（Process ID，进程标识符）是操作系统为每个进程分配的唯一数字编号。同一时刻同一台机器上 PID 唯一。

在 Linux 中，PID 的实际含义是线程 ID：进程本身占用一个 PID（就是主线程的 TID），每个线程也有一个 TID，而 TID 的取值空间和 PID 共用同一个池。内核用 TGID（线程组 ID）来标识「进程」，用 TID 标识「线程」。

这就解释了为什么 kill -9 <pid> 能杀线程也能杀进程，而 kill -9 <tid> 只杀那一个线程（在某些实现里会杀整个线程组，行为略有差异）。

jmap -histo:live 的副作用

live 参数会强制触发一次 Full GC，才能统计出「存活对象」。代价：

  • 停顿时间可能达到数秒到数十秒（取决于堆大小和存活对象量）；
  • 对延迟敏感的生产服务，高峰期绝对不能执行；
  • 如果对象存活率高，Full GC 也回收不了多少内存，白白付出停顿代价。

替代方案：jmap -histo:<pid>（不带 live）不触发 GC，统计的是「已分配对象」，数值偏大但零影响，适合高频采样做趋势观察。

给 Java 应用的实践建议

生产环境的 Java 服务应当设成 Guaranteed：requests.cpu == limits.cpu 且 requests.memory == limits.memory。这既保证了 QoS 优先级（节点资源紧张时不会被优先杀掉），也让调度器更准确地判断节点能否承载你的 Pod。

另外，requests.memory 应该等于 limits.memory——否则节点按 requests 调度，调度完再超用，会造成节点内存压力。

Java 应用在 K8s 上的四个必知点

  1. 优雅停机K8s 发 SIGTERM 后，容器有 terminationGracePeriodSeconds（默认 30s）完成清理。JVM 收到 SIGTERM 会执行 shutdown hook。必须配合 preStop hook（如先 sleep 5s 让流量摘除）。
  2. 就绪探针与存活探针要分开readinessProbe 决定是否接流量，livenessProbe 决定是否重启。Spring Boot Actuator 的 /actuator/health/readiness 和 /actuator/health/liveness 正好对应。
  3. 内存 limit 是硬约束超过 limit 会被内核直接杀掉，没有任何 Java 层的机会。这是最需要防守的地方。
  4. CPU limit 会导致节流超过 CPU limit 会被 CFS 限流（throttling），表现为 P99 毛刺但 CPU 使用率看起来不高。用 container_cpu_cfs_throttled_seconds_total 指标排查。

CHAPTER 15

NMT：原生内存追踪完全手册

NMT（Native Memory Tracking，原生内存追踪）是 HotSpot 内建的堆外内存记账系统。它解决一个具体问题：RSS 比堆大出来的那部分，到底花在哪了？

它解决什么问题

JVM 只精确知道堆的用量。线程栈、直接内存、CodeCache、GC 的内部结构、malloc arena——这些都算在 RSS 里，但 JVM 默认不告诉你各占多少。NMT 就是给 JVM 内部加上了一本账。

一句话

堆内用 jstat / GC.heap_info 看，堆外用 NMT 看。两者合起来才能解释 RSS。

原理与限制

  • 原理JVM 内部的内存分配点（malloc、mmap、线程栈创建）被插桩，每次分配都记到对应「分类」的计数器里。查询时遍历这些计数器求和，所以是精确的分配量，不是采样估算。
  • 必须在启动时开启参数是 -XX:NativeMemoryTracking=summary 或 detail。运行中的进程无法后补开启——这是它最大的局限，意味着「等出问题了再开」这条路走不通。
  • 两种级别summary 只按分类汇总（开销小，~1%）；detail 追踪到每个分配点（开销大，~5%，且会保留更多元数据）。日常用 summary，出疑难再上 detail。
  • 无法追踪非 JVM 的 malloc如果 native 库（Netty 的 epoll、压缩库、JDBC native 部分）直接调用 glibc 的 malloc，这部分不计入 NMT。NMT 只能解释 JVM 自己的开销。
  • attach 机制要求需要 jcmd attach 到目标进程，某些精简镜像或安全策略下会被拦截。镜像里要有完整 JDK。
  • 不能和 heap dump 同时用两者都会触发 safepoint 并占用大量资源，官方建议错开执行。

基础分（必须全对）

1JVM 内存分哪几块？哪些是线程私有的？哪些会被 GC？

答：JVM 的运行时数据区分五大区 + 两大区外内存。

线程私有的三块（每线程一份，随线程生灭）：

  • 程序计数器（PC Register）：记录当前线程执行的字节码行号，是唯一不会 OOM 的区域。
  • 虚拟机栈：存放方法栈帧（局部变量表、操作数栈、动态链接、返回地址）。每个方法调用压一个栈帧，返回即弹出。
  • 本地方法栈：为 Native 方法（JNI）服务的栈，与虚拟机栈类似（HotSpot 中两者合二为一）。

线程共享的两块：

  • 堆（Heap）：存放几乎所有对象实例和数组，是 GC 的主战场。
  • 方法区（Metaspace）：JDK 8 起在堆外，存放类元数据、运行时常量池、方法字节码。

堆外但线程共享的：直接内存（ByteBuffer.allocateDirect）、Code Cache、GC 内部结构、malloc arena。

会被 GC 的：主要是堆。Metaspace 不走常规 GC，但会在类加载器卸载时释放内存。栈不需要 GC，因为栈帧的生命周期是确定的——方法返回必然销毁，栈上的引用随之失效，GC 没有介入的必要。

2为什么说「只有堆和 Metaspace 有 GC」？栈为什么不需要 GC？

答：这句话是对标准答案的精炼，但更严谨的表述是：GC 只管理堆里的对象。

为什么栈不需要 GC：GC 的前提是「无法静态判断对象是否还活着」，需要从 GC Roots 做可达性分析。而栈上的对象生命周期是确定性的——方法进入压栈、方法返回出栈，必然销毁。栈帧结构由编译器静态确定，可以像函数调用一样精确管理。用 tracing GC 去扫栈既无意义，开销又巨大。

栈上只存基本类型的值和堆对象的引用，引用指向的对象被回收后，这些引用自然变成 null，栈帧本身也随之销毁。

Metaspace 的特殊性：它没有专门的 GC 线程，而是靠「类卸载」释放——当一个 ClassLoader 加载的所有类都不再可达、且该 ClassLoader 本身也不可达时，它占用的 Metaspace 被回收。所以 Metaspace 泄漏的根因永远是类加载器泄漏。

3一个普通 Java 对象占多少字节？为什么要考虑对齐填充？

答：对象大小 = 对象头 + 字段数据 + 对齐填充。

64 位 JVM、开启压缩指针（-XX:+UseCompressedOops，默认开启）的典型情况：

  • 对象头 12 字节：Mark Word 8 字节（存哈希码、GC 分代年龄、锁状态）+ 类型指针 4 字节（压缩指针）。不开启压缩指针则是 8 + 8 = 16 字节。
  • 字段数据：按字段类型累加，boolean/byte 1 字节，char/short 2 字节，int/float 4 字节，long/double 8 字节。
  • 对齐填充：0~7 字节，把对象总大小补齐到 8 字节的整数倍（-XX:ObjectAlignmentInBytes 默认 8）。

具体例子：new Object() = 12 + 0 + 4（填充）= 16 字节，不是 0 字节。带 1 个 int 字段 = 12 + 4 = 16 字节。带 1 个 long 字段 = 12 + 8 = 20 → 填充 4 → 24 字节。

为什么必须考虑对齐：一是保证 CPU 按机器字长（8 字节）访问内存，避免跨字长读取降低性能；二是 JVM 的指针压缩（-XX:+UseCompressedOops）依赖 8 字节对齐才能用 4 字节表示堆内偏移量；三是某些硬件平台要求原子访问必须对齐。

4进程的 RSS 和 -Xmx 是什么关系？为什么不等？

答：RSS（Resident Set Size）是进程当前实际驻留在物理内存中的页数总和。-Xmx 限制的是堆的上限。两者是「包含」关系，不是「相等」关系：RSS ⊃ 堆 committed ⊃ 存活对象，堆只是 RSS 的一部分。

RSS 大于 -Xmx 的原因有六：

  1. 堆外内存：线程栈、Metaspace、Code Cache、直接内存、GC 内部结构，全都不计入 -Xmx。
  2. 堆的 committed 可能大于 used——已申请但没有对象占用的页仍算在 RSS 里。
  3. used 里包含垃圾，live set 通常只有 used 的 30%~70%。
  4. GC 不一定及时归还内存给操作系统。
  5. glibc 的 malloc arena 与内存碎片（多线程程序尤其明显）。
  6. JNI 与 native 库分配的内存。

推论：容器 limit 必须显著大于 -Xmx（经验值 50%~60%），否则堆还没满进程就被内核杀了。这就是「为什么不能把 -Xmx 设成等于容器 limit」的答案。

5-Xms 和 -Xmx 为什么建议设成一样？

答：-Xms 是「已向操作系统申请并映射的物理页」，-Xmx 只是「JVM 允许增长的上限」。两者不等会带来三个问题：

  1. 扩缩容造成延迟毛刺：堆需要增长时，JVM 必须向 OS 申请新内存并逐页 touch（触发缺页中断），这个过程是 STW 的，会在流量高峰打出毛刺。
  2. RSS 曲线锯齿：缩容时归还内存给 OS，再扩容又要重新申请，oom_score 随之变化，在容器里可能导致还没到 limit 就被提前 OOMKill。
  3. RSS 不可预测：运维无法准确预估容器内存占用。

结论：生产环境一律 -Xms = -Xmx。唯一例外是「快速失败」场景——故意把 -Xmx 设得很小，让 OOM 尽早暴露，属于特殊用途。

6G1、ZGC、ParallelGC 各自的适用场景？CMS 为什么被移除了？

答：

Parallel GC（-XX:+UseParallelGC）：吞吐优先，全部用并行线程做 GC，不追求低停顿。适合批处理、离线任务、大数据计算等延迟不敏感的场景。缺点是 Full GC 停顿长。

G1（JDK 9+ 默认）：把堆切成 Region 统一管理，年轻代老年代不再是物理分界，通过「Remembered Set」追踪跨代引用，可以只回收部分老年代而不需要 Full GC。通过 -XX:MaxGCPauseMillis（默认 200ms）作为暂停时间目标。适合 4GB~64GB 堆、延迟要求中等偏严的通用场景。

ZGC（-XX:+UseZGC）：用染色指针（colored pointers）和读屏障实现并发标记与并发压缩，停顿时间与堆大小无关（亚毫秒级），支持 TB 级堆。代价是额外 10%~20% 的 CPU 开销和一定内存开销。适合大堆（>100GB）、超低延迟要求、内存成本可接受的场景。

CMS 为什么被移除，三个原因：

  1. 碎片化：CMS 用标记-清除算法，不整理内存。并发标记期间新对象持续分配，会触发 promotion failed，被迫执行 Full GC——而且此时已降级为单线程压缩式 Full GC，停顿极长。
  2. 浮动垃圾：CMS 只能清除已标记的对象，标记结束后进入并发清扫阶段的对象会堆积到下次 GC，表现为内存占用先涨后降。
  3. 维护成本：调优参数众多且与其他收集器行为差异大，存量代码里的 CMS 参数无法平滑迁移。

时间线：JDK 8 与 CMS + Parallel Old 的组合共存；JDK 9 G1 成为默认；JDK 14 正式弃用 CMS；JDK 17 彻底移除，-XX:+UseConcMarkSweepGC 会直接启动失败。

7什么是 Humongous 对象？阈值怎么算？

答：Humongous（巨型）是 G1 特有的对象分类。G1 把堆切分成等大的 Region，对象大小 ≥ Region 大小的一半 时，被判定为 Humongous 对象，直接分配在连续的 Humongous Region 上。

阈值计算：Region 大小由 -XX:G1HeapRegionSize 指定，必须是 1 的幂，范围 1MB ~ 32MB，且不超过堆大小的 1/2048。默认是堆大小的 1/2048，向上取到 2 的幂。例如 8GB 堆 → Region = 4MB → Humongous 阈值 = 2MB。

为什么要有这个分类：G1 的 Region 是固定大小的，普通小对象如果跨 Region 分配会产生大量碎片引用。G1 选择让大对象独占连续 Region，牺牲一点外部碎片来换取引用管理简单。

风险：

  • Humongous 对象只能分配在连续空闲 Region 上，分配失败会触发并发失败（Concurrent Cycle）甚至 Full GC。
  • 大数组（比如 2MB 的 byte[]）很容易踩线，导致明明堆还有很多空闲却频繁 Full GC。
  • 默认 Region 越小，Humongous 阈值越低，踩线概率越高。4GB 堆默认 Region = 2MB，阈值 1MB，一个 1MB 的数组就成了 Humongous。

应对：调大 -XX:G1HeapRegionSize（比如 16MB）抬高阈值；或避免创建巨型数组（分块处理）。

8什么是晋升失败？会带来什么后果？

答：晋升失败（Promotion Failure）指：Minor GC 结束时，需要晋升到老年代的对象无法被放入（Survivor 放不下、或老年代剩余空间不足）。它的直接后果是触发 Full GC。

成因：老年代被长期存活对象占满（缓存、连接池、大 session），而 GC 后仍腾不出空间；或同年龄对象总量过大，超过 Survivor 空间；或 Humongous 对象分配失败。

后果链条：晋升失败 → Full GC → 回收后仍放不下 → 堆重构（Heap Retrashing，把存活对象重新整理压缩）→ CPU 飙高 + 停顿数秒 → 请求堆积超时 → 上游雪崩。这正是「明明堆内存还剩很多，却频繁 Full GC」的典型解释。

排查：

  • GC 日志里搜 to-space exhausted 或 promotion failed；
  • jstat -gccause <pid> 看最后一次 Full GC 的原因是否为 promotion failure 或 G1 Evacuation Pause；
  • 看老年代使用率是否长期高于 80%；
  • 用 jmap -histo:live 找出到底什么对象占着老年代不放。

进阶分（要能结合案例）

9容器里为什么会出现 OOMKilled 而不是 OutOfMemoryError？

答：因为触发者不同。

OutOfMemoryError 是 JVM 自己抛的：JVM 尝试分配内存失败，且它管理这个区域，知道原因，于是在堆栈里抛出带明确信息的异常——Java heap space / Metaspace / Direct buffer memory / unable to create new native thread。

OOMKilled 是 Linux 内核干的：进程的 RSS 超过了 cgroup memory limit，cgroup 的 memory controller 触发 OOM killer，直接给进程发 SIGKILL。内核不理解也不关心这是 Java 还是 Nginx，它只知道「这个进程占的物理内存超了」。

为什么容器里更容易遇到 OOMKilled：容器有硬性 limit，物理内存用完就立刻被杀；而裸机通常有 swap，JVM 有机会先抛 OOM、GC 也能喘口气。容器里没有这个缓冲。

典型场景：JDK 8 的 JVM 看到的是宿主机内存（比如 64GB），按 1/4 算出 16GB 堆，但容器 limit 只有 2GB —— 进程刚启动就超过 limit 被杀，JVM 根本还没来得及做任何 GC。

判定：kubectl describe pod 里 Reason: OOMKilled、Exit Code: 137、dmesg 里的 Memory cgroup out of memory、cgroup 的 memory.events 里 oom_kill 计数大于 0。

10JVM 感知 cgroup 的机制是什么？什么版本开始支持？有什么坑？

答：

机制：JDK 10 引入 -XX:+UseContainerSupport（默认开启），JVM 启动时读取 cgroup 的内存限额文件（v1 的 memory.limit_in_bytes，v2 的 memory.max），用它来计算默认堆大小（-XX:MaxRAMPercentage 默认 25%，即堆默认取 limit 的 1/4），而不是按宿主机物理内存。同时也会感知可用处理器数（UseContainerSupport 同样影响 active_processor_count）。

版本：

  • JDK 8u191 起回移植了容器感知能力（当年主要是为了跑在容器里的性能优化）。
  • JDK 10 正式引入并成为默认行为。
  • JDK 8 早期版本（8u191 之前）完全没有这个机制，默认堆按宿主机内存算，这是容器时代最早的 OOMKilled 根因。

坑：

  1. cgroup v2 的嵌套层级：理论上 JVM 应取所有父级 limit 的最小值。但在多层限制的环境（K8s limit + 节点级 limit + 命名空间 limit）中，JVM 可能计算错误——这是 OpenJDK 的已知问题（JDK-8322420）。
  2. 只影响默认值，不影响显式配置：如果你显式设了 -Xmx，容器感知的结果就不参与计算了。
  3. 只管堆，不管堆外：容器感知只影响堆大小的默认值，直接内存、线程栈、Metaspace 都不受它约束。
  4. 与 -XX:MaxRAMPercentage 混淆：MaxRAMPercentage 是基于容器 limit 的百分比，InitialRAMPercentage 是初始堆百分比。

结论：容器环境永远显式指定 -Xmx，不要依赖默认值。这是 AWS 官方《JVM 内存、CPU 与 Classpath 在 AWS 容器上的最佳实践》里明确给出的结论。

11怎么区分「内存泄漏」和「分配速率过快」？给出判据。

答：核心判据是「GC 之后能不能降下来」。

方法 1：观察 GC 后的基线（最可靠）

  • 泄漏：每次 Full GC 后，老年代使用量呈阶梯式单调上升，基线不断抬高。例如 2GB → 2.5GB → 3GB → 3.5GB。说明有东西永远不释放。
  • 分配速率过快：Full GC 后老年代回落到稳定的低位（比如始终在 1GB 上下），只是两次 GC 之间涨得很快。说明没有泄漏，只是产生垃圾的速度超过了回收速度。

方法 2：看 GC 频率与回收量的比值

  • 泄漏：GC 越来越频繁，但每次回收的量越来越少（能回收的都回收了，剩下的都活着）。
  • 速率过快：GC 频繁，但每次回收量基本稳定，堆的使用率在「低位 → 高位」之间周期性震荡。

方法 3：看对象年龄分布　用 jmap -histo:live：泄漏场景下，老年代对象数量持续增长；速率过快场景下，对象数量稳定，只是周转快。

方法 4：压测对照实验　用固定的内存配置跑压测，如果降低 QPS 后内存能稳定下来，那是速率问题；无论 QPS 多低内存都单调上涨，那是泄漏。

处置方向完全不同：速率过快 → 调大堆、换更高效的 GC、减少中间对象；泄漏 → 找到那个不放手的东西（静态集合、ThreadLocal、类加载器、缓存无界）。

12什么是类加载器泄漏？为什么它会同时污染堆和 Metaspace？

答：类加载器泄漏是指某个 ClassLoader 已经「逻辑上该死了」——它加载的所有类都不再被业务引用——但它自己仍然被某个强引用链吊住，导致它加载的所有类元数据永远无法卸载。

为什么同时污染堆和 Metaspace：

  • Metaspace 侧：类的元数据、方法字节码、常量池都在 Metaspace。ClassLoader 不可达 → 它的 Metaspace 才能被释放。被吊住 → Metaspace 无限增长。
  • 堆侧：静态字段。一个类的静态字段持有它引用的对象，而这些对象可能又引用更多对象。只要类的 ClassLoader 还活着，这个「静态字段 → 对象图」就是 GC Root 可达的，整条链上的对象都不能被回收。典型例子：动态代理类的静态字段缓存了 handler，handler 又持有整个应用的上下文。

常见来源：动态代理/CGLIB 每次生成新类 + 新 ClassLoader；频繁热部署；JDBC 驱动被注册进 DriverManager（持有定义它的 ClassLoader）；Lambda 隐藏类过多；Tomcat 的 WebAppClassLoader 在重载时未卸载。

识别方法：

  • jcmd <pid> VM.classloader_stats —— 看各 ClassLoader 加载的类数量，是否有 ClassLoader 加载了类但类已被卸载；
  • jcmd <pid> VM.classloaders —— 列 ClassLoader 实例及存活状态；
  • jcmd <pid> GC.class_histogram | head -30 —— 看代理类数量是否异常；
  • 关键指标：LoadedClassCount 单调递增，而堆使用率几乎不动。
13LoadedClassCount 是什么？为什么它比堆使用率更灵敏？

答：

LoadedClassCount 是 JVM 已加载的类的总数，可以通过 jstat -class 或 Micrometer 的 jvm.classes.loaded 指标获取。它是单调递增的（除非发生 Full GC 触发的类卸载）。

为什么比堆使用率更灵敏：

  1. 每个类的成本是几十到几百 KB（元数据 + 方法字节码 + 调试信息），但一个类的元数据在堆的统计里几乎看不见——它在 Metaspace，堆使用率完全反映不出来。
  2. 类加载是「单向」的：每加载一个新类，Metaspace 占用就增加一点。堆使用率会因为 GC 波动而上下起伏，而类数量只增不减，趋势线非常干净，容易识别异常。
  3. 泄漏的早期阶段堆完全正常。典型场景：LoadedClassCount 30 分钟内从 8000 涨到 60000，堆使用率纹丝不动，Metaspace 却从 200MB 涨到 480MB。等到 Metaspace 满了报警，已经太晚了。

实战用法：把 jvm.classes.loaded 和 jvm.memory.used（nonheap）一起做监控告警。经验阈值：加载类总数超过 15000 就要警惕，超过 30000 基本可以确认有类加载泄漏（不同应用基线不同，需要自己建立基线）。

判断「持续增长」而不是「绝对值」：连续 3 个采样窗口递增超过 10%，就是信号。

14jmap -histo:live 有什么副作用？什么时候不能执行？

答：-histo:live 的 live 参数要求 JVM 先执行一次 Full GC，才能统计出真正存活的对象（不带 live 统计的是「已分配过的对象」，包含垃圾）。

副作用：

  • 停顿：Full GC 的耗时与堆大小和存活对象量正相关。8GB 堆、存活 4GB 的应用，Full GC 可能停顿 3~10 秒；32GB 堆可能几十秒。
  • 吞吐损失：Full GC 期间所有业务线程 STW，请求全部挂起。
  • 可能触发连锁反应：Full GC 后堆内存归还，可能引发后续的重新分配；某些应用在 Full GC 后行为会变（如缓存被清空）。
  • 可能失败：Full GC 期间如果应用有自己的逻辑（比如在 finalize 里做重活），会放大停顿。

什么时候不能执行：

  1. 业务高峰期——绝不能执行。1 分钟的全局停顿在流量高峰就是事故。
  2. 延迟敏感的服务（交易、支付、实时音视频）——任何时候都不合适。
  3. 堆特别大（>16GB）——停顿不可控。
  4. 磁盘空间不足的机器——dump 会写满磁盘。

安全替代方案：

  • 用 jmap -histo:<pid>（不带 live）——不触发 GC，零停顿，数值偏大但可做趋势分析；
  • 用 jcmd <pid> GC.class_histogram（JDK 9+）——同样不触发 GC；
  • 用 JFR 的 OldObjectSample 事件采样——开销约 1%，能拿到存活对象样本；
  • 在预发环境复现，用 -XX:+HeapDumpOnOutOfMemoryError 自动 dump。
15JFR 的开销大概多少？适合什么场景？

答：JFR（Java Flight Recorder）是 JDK 11+ 内建的低开销生产级性能剖析器。

开销：

  • default 配置：约 1%（官方数据，通常在 0.5%~2% 之间）
  • profile 配置：约 2%（更细的事件采样，官方文档给出的典型值）
  • 典型场景下 < 1.5%，可以作为常驻配置

关键在于它用环形缓冲区 + 采样 + 事件驱动的技术，而不是全量追踪；数据在 JVM 内存中，超过缓冲区就覆盖最老的记录，不会无限增长。

适合什么场景：

  • 生产环境的常规采集——这是它最大的价值。Arthas、async-profiler 需要额外 agent，JFR 是 JVM 原生的。
  • CPU 热点定位——jdk.ExecutionSample 给出方法级火焰图。
  • 内存分析——jdk.OldObjectSample 可以近似替代 jmap -histo:live，但无停顿。
  • 分配分析——jdk.ObjectAllocationSample 定位大对象分配点，这是找内存泄漏的利器。
  • GC 与锁竞争——jdk.GCPhasePause、jdk.JavaMonitorEnter。
  • IO 异常——jdk.FileRead、jdk.SocketRead 能看到慢调用。

使用方式：

# 启动时录制
java -XX:StartFlightRecording=duration=300s,filename=app.jfr,settings=profile -jar app.jar

# 运行时动态开启（不需要重启）
jcmd <pid> JFR.start name=diag duration=300s filename=/data/app.jfr settings=profile
jcmd <pid> JFR.dump name=diag filename=/data/app.jfr   # 提前落盘
jcmd <pid> JFR.stop name=diag

# JDK 11+ 也可以用 jfr 命令分析
jfr summary app.jfr
jfr print --events jdk.OldObjectSample app.jfr

注意事项：settings=profile 开销更高（约 2%），但事件更全；duration 到期后录制自动停止并落盘；容器里要确保 filename 指向挂载的持久卷，否则 Pod 一重建文件就没了。

16什么是 NMT？它解决什么问题？

答：NMT（Native Memory Tracking，原生内存追踪）是 HotSpot 内建的堆外内存记账系统。

解决什么问题：JVM 只精确知道堆的用量。线程栈、直接内存、CodeCache、GC 内部结构、Metaspace 这些都在 RSS 里，但默认不告诉你各占多少。当你在容器里看到「RSS 7GB，堆只用了 2GB」时，NMT 是唯一能告诉你这 5GB 去向的工具。

工作原理：JVM 内部的内存分配点被插桩，每次分配都记入对应分类的计数器。查询时遍历计数器求和，所以是精确的分配量而非采样估算。分为几个大类：Java Heap、Class（Metaspace）、Thread（栈 + TLS）、Code、GC、Compiler、Internal、Other。

用法：

# 启动时开启（必须，无法后补）
-XX:NativeMemoryTracking=summary    # 开销 ~1%
-XX:NativeMemoryTracking=detail    # 开销 ~5%，更细

# 查询
jcmd <pid> VM.native_memory summary scale=MB
jcmd <pid> VM.native_memory baseline /tmp/base.txt
jcmd <pid> VM.native_memory summary.diff scale=MB

局限：必须在启动时开启；无法追踪非 JVM 的 native malloc（Netty 的 epoll、glibc arena、JDBC native 部分）；Total 不等于 RSS；detail 模式开销明显。

生产建议：常驻开 summary 模式。开销可忽略，但能让你在半夜被叫醒时立刻回答「堆外这 2GB 是什么」。

17遇到 P99 毛刺，你的排查顺序是什么？

答：我按「先分清是延迟还是错误，再定位在哪一层，最后找根因」的顺序走。给一个可执行的 checklist：

  1. 确认毛刺是真实的：是不是客户端超时设得太短？网络抖动？先看全局 P99 和 P999 的曲线形状——是尖峰还是台阶。尖峰通常是单次事件（GC、部署、慢查询），台阶通常是持续性问题（流量上涨、缓存失效、锁竞争）。
  2. 确认在哪一层：区分是 JVM 停顿、下游依赖慢、还是自身线程池排队。看 http_request_duration_seconds 的服务端耗时 vs 客户端耗时；看应用自身的 tomcat_threads_busy。
  3. 看 GC：jstat -gcutil 看 Full GC 频率和停顿；jstat -gccause 看触发原因。Full GC 是第一嫌疑人，但不要一上来就认定——先确认时间戳是否对得上。
  4. 看线程状态：jstack 多采几次（间隔 5~10 秒），看是否大量线程 BLOCKED 在同一把锁上，或者 WAITING 在下游连接上。
  5. 看下游：数据库慢查询日志、Redis 延迟、第三方接口。Java 服务里 70% 以上的「毛刺」根因在下游。
  6. 看资源：CPU 是否打满？是否被 CFS 限流（container_cpu_cfs_throttled_seconds_total）？网络重传？磁盘 IO 延迟？
  7. 采样剖析：以上都正常，用 JFR 录一段（settings=profile，开销 2%），看火焰图里 CPU 到底花在哪；再看 jdk.ObjectAllocationSample 是否有异常分配。
  8. 区分「偶发」与「必然」：能否在预发复现？能否用压测放大？

关键是「时间对齐」：所有证据必须能对齐到同一个时间轴。毛刺排查失败的最常见原因，不是不会用工具，而是看了不同时间窗的数据（比如 GC 日志看的是今天，监控看的是昨天）。

18如果要调 Region 大小，代价是什么？为什么不能只调参数？

答：

Region 大小怎么定的：-XX:G1HeapRegionSize，必须是 1 的幂，范围 1MB ~ 32MB，且不超过堆大小的 1/2048。默认取堆的 1/2048 向上取整到 2 的幂。Region 是 G1 的基本管理单位—— Eden、Survivor、老年代都只是「Region 的逻辑标签」，Region 可以整体被回收复用。

调大的代价：

  • Humongous 阈值抬高（Region/2），巨型对象问题缓解——这是主要收益。
  • Region 数量减少：8GB 堆 + 4MB Region = 2048 个 Region；改成 16MB = 1024 个。Remembered Set 的条目数减少，扫描效率提升。
  • 但堆的「最小回收单位」变粗：Mixed GC 回收粒度变大，回收更不精确，可能出现「回收了 4 个 Region 但只有一个有垃圾」的浪费。
  • 空闲 Region 的碎片风险上升：G1 优先使用连续空闲 Region，大 Region 下更难找到合适的连续空间。
  • 停顿时间变长：单次回收涉及的 Region 更大，MaxGCPauseMillis 目标更难达成。

调小的代价：Region 变小 → 数量变多 → Remembered Set 内存和 CPU 开销上升；Humongous 阈值降低，更容易踩线（比如 Region=2MB 时，1MB 的数组就成了 Humongous）；单次回收粒度小，停顿更短但更频繁。

为什么不能只调参数：

  1. Region 大小是「因」不是「果」。它由堆大小和 G1 的自动设计决定。如果真正的问题是「堆太小导致 GC 过于频繁」，调 Region 大小只会掩盖症状，GC 次数不会减少。
  2. 它只是三个杠杆之一。影响 GC 效率的至少还有：堆大小（决定分配速率与 GC 频率的比值）、MaxGCPauseMillis（决定暂停目标，进而决定 Mixed GC 的激进程度）、以及应用本身的分配速率。真正高杠杆的往往是减少分配（对象池、避免不必要的装箱、复用缓冲区）。
  3. 参数之间会互相牵制。比如把 MaxGCPauseMillis 调小到 50ms，G1 会更保守（每次只回收少量 Region），可能导致回收跟不上分配速度，反而增加 Full GC 频率。
  4. 必须用数据验证。调整后要看：GC 总时间占比、Full GC 次数与原因、老年代回收效率、P99 延迟。没有这些数据支撑的调参是玄学。

我的做法：先问「GC 总时间占 CPU 的百分之多少、Full GC 频率是多少」，如果 GC 总开销 < 5% 且无 Full GC，就不动 GC 参数——此时毛刺多半不是 GC 造成的。

19什么情况下你会从 G1 换到 ZGC？换的代价怎么评估？

答：

什么情况下换（按收益从大到小）：

  1. 堆很大（> 100GB）且延迟要求严——这是最典型的场景。G1 在大堆上的 Mixed GC 扫描成本随堆增长，停顿难以稳定控制；ZGC 的停顿时间与堆大小无关（亚毫秒级）。
  2. Full GC 频繁且不可接受——G1 的并发失败在大堆 + 高分配速率下容易触发，退化成 Full GC 后停顿数秒；ZGC 基本没有 Full GC。
  3. 业务对尾延迟极敏感——金融交易、实时音视频、对超时有严格 SLA 的接口。
  4. 内存成本可以接受——ZGC 需要额外的元数据和并发线程。

什么情况下不该换：堆小于 16GB（G1 已经足够好，ZGC 优势不明显）；CPU 紧张（ZGC 额外开销 10%~20% CPU）；吞吐优先的批处理（Parallel GC 更合适）。

换的代价怎么评估：

  1. 先确认瓶颈真的在 GC。用 jstat 和 GC 日志量化：GC 总时间占 CPU 的比例、Full GC 次数与停顿、P99 与 GC 停顿时长的相关性。如果 GC 只占 3% 的 CPU，换收集器不会有任何效果。
  2. 在预发环境做对照压测。同一份压测脚本，分别用 G1 和 ZGC 跑，比较：吞吐、P50/P99/P999、最大停顿、GC CPU 占比、RSS 峰值。
  3. 在生产做灰度。先 1 个 Pod 切 ZGC，对比同期的 GC 指标、延迟指标、内存指标。不要一次全切。
  4. 量化 CPU 成本。ZGC 的并发线程会占用 CPU，在 CPU limit 严格的容器里可能触发 CFS 限流，反而拖累延迟——这是最容易被忽略的代价。
  5. 量化内存成本。ZGC 有额外的元数据开销和更大的堆占用，需要相应调大容器 limit。
  6. 考虑回滚方案。保留 G1 的启动参数配置，确保能快速切回。

我的取舍倾向：没有明确的延迟 SLA 要求就不换。G1 的默认配置已经能覆盖绝大多数业务。换收集器是有成本的技术债，不是免费的性能提升。

20如何设计一套「让内存问题可控失败」的机制？

答：核心理念：让故障以「可诊断、可恢复、低影响」的方式暴露，而不是以「静默被杀、影响面不可控」的方式崩溃。从五层设计：

  1. 预防层：把内存预算写清楚并强制执行
    • 容器 limit > -Xmx + 堆外预估 + 15% 缓冲；
    • 显式设置 -XX:MaxMetaspaceSize、-XX:MaxDirectMemorySize、-XX:ReservedCodeCacheSize；
    • 堆外预算用 NMT 实测校准，不是拍脑袋。
  2. 观测层：让泄漏在变成事故之前被发现
    • 监控 LoadedClassCount 增速（类加载泄漏的最灵敏指标）；
    • 监控 jvm_memory_bytes_used{area="nonheap"} 斜率；
    • 监控 process_resident_memory_bytes 与 limit 的比值；
    • 监控 GC 频率、Full GC 次数、老年代使用率；
    • 预警要基于斜率而非绝对值。
  3. 诊断层：出问题时能拿到证据
    • -XX:+HeapDumpOnOutOfMemoryError + -XX:HeapDumpPath 指向持久卷；
    • 开启 GC 日志（-Xlog:gc*:file=/data/gc.log:time,uptime:filecount=10,filesize=50M）；
    • 常驻 -XX:NativeMemoryTracking=summary；
    • JFR 常驻或可快速动态开启；
    • 镜像里要有完整 JDK，jcmd/jstack 可用。
  4. 失败层：崩溃方式要可控
    • 无状态服务：-XX:+ExitOnOutOfMemoryError + K8s 自动重建。比半死不活好。
    • 有状态服务：不要立刻退出，先限流/降级，等 K8s 的 readiness 探测失败再摘流量。
    • 配置：堆、Metaspace、直接内存全部设上限，让每种溢出都以明确的 OutOfMemoryError 形式出现，而不是被内核杀掉。
  5. 兜底层：外部资源也要有边界
    • 线程池全部有界（ThreadPoolExecutor 的 maxPoolSize、队列容量都要设）；
    • 数据库连接池设上限（maxPoolSize），连接池无限是最常见的雪崩源；
    • MQ 消费者要限流，防止拉垮下游；
    • 缓存要有最大容量和淘汰策略（expireAfterWrite + maximumSize）。

一句话总结：让 OOM 变成一个带着堆栈和 dump 的 Java 异常，而不是一个没有线索的 exit 137。前者 5 分钟定位，后者可能查一夜。

21容器里堆外的每一块内存，你打算怎么分配和监控？

答：我按「先测量、再分配、再验证」的思路做。

第一步：测量——不猜，先测。在预发和生产开 -XX:NativeMemoryTracking=summary，用 jcmd <pid> VM.native_memory summary scale=MB 拿到每个分类的真实 committed 值。这是唯一可靠的基线。

第二步：分配——用测量值反推预算：

块分配方式监控
线程栈-Xss512k + 线程数上限（线程池必须设界）NMT 的 Thread 分类 + process_threads
Metaspace-XX:MaxMetaspaceSize（实测值 × 1.5）NMT 的 Class 分类 + jvm.classes.loaded 增速
直接内存-XX:MaxDirectMemorySize（按业务量估）NMT 的 Other/Internal 分类 + 应用埋点
Code Cache-XX:ReservedCodeCacheSize=256mNMT 的 Code 分类
GC 结构间接控制（堆的 5~10%）NMT 的 GC 分类
malloc arena环境变量 MALLOC_ARENA_MAX=2RSS 与 NMT Total 的差额（就是 arena + 非 JVM 部分）
安全缓冲limit 的 10~15%container_memory_working_set_bytes / limit 告警

第三步：验证——上线后用 NMT 的 baseline + summary.diff 做周期性 diff，确认没有意外增长项。同时压测到极限，看 RSS 峰值离 limit 还有多少余量。

核心监控指标（4 个 + 1 个兜底）：

  1. jvm_memory_used_bytes{area="heap"} + GC 后基线
  2. jvm_memory_used_bytes{area="nonheap"}（Metaspace）
  3. jvm_classes_loaded（斜率告警）
  4. process_resident_memory_bytes（RSS）
  5. 兜底：container_memory_working_set_bytes / limit 的比值 > 80% 告警

为什么 NMT 必须常开：它必须在启动时启用，无法后补。如果不常开，凌晨告警时你想查「堆外这 2GB 是什么」，只能靠猜。这 1% 的开销换确定性，非常值。

22一个系统从 G1 换成 ZGC，你怎么说服团队？

答：我不会用「ZGC 更好」来说服，而是用业务指标 + 可回滚的灰度方案来说服。

第一步：先证明瓶颈在 GC（这是能否说服的关键）

拿出数据：GC 总耗时占 CPU 的比例、Full GC 次数与平均停顿、P99 延迟与 GC 停顿时长的相关性曲线。如果 GC 只占 3% 的 CPU，我主动放弃这个提案——因为换了不会有任何收益，团队凭什么承担风险？

反过来说，如果数据是「GC 占 18% CPU，每月 3 次 Full GC 造成 20 秒的服务不可用，P99 有 4 个尖峰与 GC 停顿完全对齐」，那这就是一个有明确损失、有明确归因的问题，技术方案自然好谈。

第二步：把问题翻译成业务语言

不说「G1 的 Mixed GC 在大堆上效率下降」，说「每月有 3 次服务降级，每次影响约 X 个请求、Y 分钟，估算业务损失 Z 万元」。让团队能拿这个数字去和其他需求排优先级。

第三步：给出保守的方案

  • 灰度范围：先 1 个 Pod（1/10 流量），观察 1~2 周；
  • 回滚方式：改一行环境变量，Pod 重建即回滚，不需要发版（所以参数要放在 ConfigMap 里，不进镜像）；
  • 对比方法：同期对比（同一时间段、同一流量比例），而不是历史对比；
  • 成功标准：事先写死——Full GC 归零、P99 下降 ≥ X%、GC CPU 占比下降 ≥ Y%、错误率无上升。没有预设标准就没有说服力。

第四步：主动讲代价

我会主动说清 ZGC 的成本：CPU 开销增加 10%~20%、内存占用上升、需要重新校准容器 limit、ZGC 的调优经验比 G1 少（踩坑时能参考的案例也少）。把风险摊开讲，反而更能建立信任。

第五步：兜底

如果灰度一周后指标没达到预期，我主动提出回滚，并且不会为此感到遗憾——技术实验本来就允许失败，怕的是没有预设退出标准、硬撑着上线。

总结：说服团队靠的不是「新技术更好」，而是「问题有据可依、方案可回滚、代价已摊开、成功标准已约定」。

最后一句提醒：这份文档覆盖的是「机制与认知」。真正的掌握标准是——下次遇到线上内存告警时，你能在 5 分钟内说出「这是内部 OOM 还是外部 OOM，证据在哪一块，下一步做什么」。能做到这一点，这 16 章就真的变成你的了。
